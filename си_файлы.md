# **1. Общие требования ко всем заданиям**

Все три задания считаются выполненными только при соблюдении как функциональных, так и нефункциональных требований..

## **1.1. Обязательные требования к коду**

- Стандарт языка — C11 или новее без использования расширений компилятора в основной логике.

- Все операции открытия файлов выполняются через fopen() с обязательной проверкой результата на NULL.

- Каждый успешно открытый файл должен быть закрыт через fclose(). Результат fclose() для файлов, в которые выполнялась запись, должен проверяться.

- Ошибки чтения и записи должны отличаться от нормального достижения конца файла. Для этого необходимо использовать возвращаемые значения функций, а при необходимости feof() и ferror().

- Запрещён шаблон while (!feof(file)). Цикл чтения должен управляться результатом fgets(), fread(), fscanf() либо другой реально выполняющей чтение функции.

- Нельзя предполагать, что один вызов fread() или fwrite() всегда обрабатывает весь запрошенный объём. Для потокового копирования и сериализации необходимо корректно обрабатывать фактически прочитанное/записанное количество элементов.

- Любой пользовательский или файловый ввод чисел должен проверяться. Если используется strtol()/strtoul(), должны проверяться endptr, errno и границы целевого типа.

- Запрещены gets(), strcpy() без доказанной достаточности буфера, sprintf() без ограничения размера, а также запись за границы массивов.

- Пути к входным и выходным файлам не должны быть «зашиты» абсолютными путями в исходный код. Они передаются через аргументы командной строки либо задаются относительными путями.

- При ошибке программа должна завершаться предсказуемо: вывести понятное сообщение в stderr, освободить динамическую память, закрыть уже открытые файлы и вернуть ненулевой код завершения.

## **1.2. Ограничения**

- Нельзя читать весь входной файл в память целиком, если это прямо не разрешено в конкретном задании. Решение должно оставаться работоспособным на файлах размером в сотни мегабайт.

- Нельзя использовать системные команды shell (cat, cp, sort, sed, PowerShell и т. п.) для выполнения основной работы программы.

- Нельзя считать бинарный дамп структуры C переносимым форматом хранения. Если задание требует переносимого формата, поля должны сериализоваться явно.

- Нельзя молча игнорировать повреждённые записи, если в требованиях указано, что они должны диагностироваться.

- Запрещено заменять основную файловую обработку высокоуровневыми нестандартными библиотеками.

# **2. Задание № 1. Анализатор большого текстового журнала**

Разработать консольную программу, которая потоково обрабатывает текстовый файл журнала событий, проверяет корректность каждой строки, собирает статистику и формирует итоговый отчёт. 

## **2.1. Формат входного файла**

Каждая логическая запись занимает одну строку и имеет следующий формат:

YYYY-MM-DD HH:MM:SS;LEVEL;USER;ACTION;DURATION\_MS

Пример:

2026-09-16 10:15:02;INFO;ruslan;login;18  
2026-09-16 10:15:10;WARN;anna;open\_report;245  
2026-09-16 10:15:17;ERROR;ivan;save\_document;830

| **Поле** | **Требования** |
| - | - |
| Дата и время | Ровно 19 символов: YYYY-MM-DD HH:MM:SS. Необходимо проверить хотя бы синтаксическую форму и диапазоны: месяц 1–12, часы 0–23, минуты/секунды 0–59. |
| LEVEL | Только INFO, WARN или ERROR. Регистр учитывается. |
| USER | 1–31 символ, допустимы латинские буквы, цифры, \_ и -. |
| ACTION | 1–63 символа, допустимы латинские буквы, цифры, \_ и -. |
| DURATION\_MS | Целое число от 0 до 3 600 000 включительно. |


## **2.2. Интерфейс командной строки**

./log\_analyzer input.log report.txt invalid.log

Аргументы:

- input.log — исходный журнал. Открывается только для чтения.

- report.txt — итоговый отчёт. Создаётся заново.

- invalid.log — файл, куда дословно записываются некорректные строки с их номерами и причиной отклонения.

## **2.3. Функциональные требования**

- Читать файл последовательно, не загружая его полностью в память.

- Поддерживать строки длиной до 1024 байт включительно. Если фактическая строка длиннее буфера, программа обязана распознать переполнение строки, дочитать её остаток до \\n/EOF и отметить такую запись как некорректную. Нельзя разбирать обрезанный фрагмент как полноценную запись.

- Удалять завершающий \\n; корректно работать и с последней строкой без символа новой строки.

- Для каждой строки проверять наличие ровно пяти полей, корректность каждого поля и отсутствие лишних данных.

- Некорректная строка не должна останавливать анализ всего файла, если чтение файла в целом возможно.

- Вести отдельные счётчики INFO, WARN, ERROR, валидных и невалидных строк.

- Для валидных записей вычислить минимальную, максимальную и среднюю длительность DURATION\_MS.

- Определить пользователя с наибольшим числом валидных событий. При равенстве выбрать лексикографически меньший USER.

- Определить ACTION с наибольшей средней длительностью среди действий, встретившихся не менее 3 раз.

- Сформировать текстовый отчёт в строго определённом формате.

- После завершения чтения проверить ferror(input). Простое получение EOF не является ошибкой.

## **2.4. Требуемый формат отчёта**

TOTAL\_LINES=1500  
VALID\_LINES=1472  
INVALID\_LINES=28  
INFO=1100  
WARN=291  
ERROR=81  
MIN\_DURATION\_MS=0  
MAX\_DURATION\_MS=3120  
AVG\_DURATION\_MS=47.63  
TOP\_USER=ruslan;EVENTS=94  
SLOWEST\_ACTION=export\_pdf;AVG\_MS=713.25;COUNT=8

Если валидных записей нет, числовые агрегаты должны выводиться как N/A, а не как фиктивные нули. Если ни одно действие не встретилось 3 раза, SLOWEST\_ACTION=N/A.

## **2.5. Требования к invalid.log LINE 17: invalid LEVEL | 2026-09-16 10:17:31;DEBUG;anna;login;10  
LINE 52: DURATION\_MS out of range | 2026-09-16 10:20:01;INFO;ivan;save;9000000**

Одна некорректная входная строка должна приводить ровно к одной диагностической записи. Для слишком длинной строки допустимо сохранить только первые 200 исходных символов и добавить маркер \[truncated\], чтобы диагностический файл не становился неконтролируемо большим.

## **2.6. Требования к памяти и структуре программы**

- Размер памяти, используемой для хранения одной строки, не должен зависеть от размера всего файла.

- Список пользователей и действий можно хранить динамически. При каждом realloc() необходимо использовать временный указатель, чтобы не потерять исходный блок при ошибке выделения памяти.

- Разбор строки должен быть вынесен из main() в отдельную функцию.

- Сбор статистики и формирование отчёта должны быть логически разделены.

- Если для поиска разделителей используется strtok(), студент должен понимать, что функция изменяет буфер. Более предпочтителен явный разбор либо strtok\_r там, где он доступен, но решение должно оставаться совместимым с выбранной платформой.

## **2.7. Обязательные тесты**

| **№** | **Сценарий** | **Ожидаемое поведение** |
| - | - | - |
| 1 | Пустой файл | Программа завершается успешно, TOTAL\_LINES=0, агрегаты N/A. |
| 2 | Одна корректная строка без завершающего \\n | Строка должна быть обработана. |
| 3 | Неизвестный LEVEL | Строка попадает в invalid.log, анализ продолжается. |
| 4 | DURATION\_MS содержит 12ms | Строка отклоняется; частичный разбор числа недопустим. |
| 5 | Строка длиннее 1024 байт | Вся логическая строка пропускается как одна ошибочная запись. |
| 6 | Файл содержит 1 000 000 строк | Потребление памяти не растёт пропорционально размеру файла за счёт хранения самих строк. |
| 7 | Ошибка записи отчёта | Программа возвращает ненулевой код; ошибка не скрывается. |
